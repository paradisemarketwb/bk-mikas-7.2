# Насколько просто заменить или доработать экраны

Приборные экраны можно собрать заново из готовых виджетов через телефон или JSON
без перепрошивки. Произвольный новый визуальный стиль, форма стрелки, графические
ресурсы и системные страницы требуют доработки C-кода UI и новой сборки.
Архитектура позволяет выполнять эти работы отдельно от протокола Микас.

Это конструктор с ограниченным набором компонентов, а не универсальный визуальный
редактор LVGL. Ниже приведены фактические возможности текущих исходников.

## Что изменяется и где

| Изменение | Телефон / JSON без перепрошивки | Где дорабатывать код, если этого недостаточно |
|---|---|---|
| Полностью перекомпоновать приборный экран | Да: добавить/удалить виджеты, изменить их тип и координаты | `ui_core/bk_ui.c`, если нужны новые правила композиции |
| Добавить приборный экран | Да, всего до 8; исходно их 5 | Лимиты/схема — `ui_config`, навигация — `ui_core` |
| Удалить, переставить, отключить приборы | Да; хотя бы один должен остаться включённым | Не требуется для существующего лимита |
| Изменить название, ID и фон прибора | Да; фон JSON действует в светлой теме | Тёмный фон и общая тема — `ui_core` |
| Назначить существующий параметр виджету | Да, из реестра 15 метрик | Новые метрики — реестр и источник данных, см. ниже |
| Поменять диапазон, пороги, точность, единицы | Да, с особенностями конкретного виджета | Новая семантика шкалы/форматирования — `ui_widgets` |
| Дуга, стрелка, число, шкала, график | Да, выбор из 9 типов | Новый тип добавляется в C-реестр и renderer |
| Передвинуть заголовок прибора, кнопку «Меню», общий статус | Нет, их позиции заданы в коде | `ui_core/bk_ui.c` |
| Изменить форму/толщину стрелки, длину дуги, анимацию показаний | Нет | `ui_widgets/bk_widgets.c` |
| Добавить картинку, SVG, собственную иконку/фон | Нет: в JSON нет image/asset-поля | Ресурс, LVGL-объект и при необходимости новый тип виджета |
| Полностью переделать меню, Wi-Fi, DTC, настройки или заставку | Нет, это системные C-страницы | `ui_core/bk_ui.c` |
| Поменять шрифт на произвольный или загрузить новый шрифт | Нет | Новый ресурс шрифта, подключение и пересборка |
| Добавить новую физическую величину | JSON выбирает только уже существующие метрики | Телеметрия/источник; протокол меняется лишь если нужны новые данные ЭБУ |

## Что реально делает конструктор телефона

Страница, встроенная в прошивку:
[`firmware/components/wifi/index.html`](../../firmware/components/wifi/index.html).
Она позволяет выбрать тему, яркость, стартовый прибор; добавить/удалить/переставить
экраны; изменить их ID, название, фон и enabled. Для каждого виджета доступны
тип, метрика, X/Y, ширина/высота, min/max, пороги, precision, шрифт20/48,
единицы, цвет, видимость и два флага предупреждений.

Предпросмотр в браузере показывает **рамки и подписи виджетов** внутри круга.
Он не воспроизводит окончательный LVGL-рендер и не поддерживает перетаскивание
мышью: положение задаётся числовыми полями. Точный предпросмотр выполняется в
native LVGL Simulator с теми же исходниками renderer.

Правки телефона остаются в редакторе до нажатия «Сохранить в прибор».
Импорт JSON тоже сначала загружает профиль в редактор. Полная проверка полей
и геометрии выполняется прошивкой при сохранении; предварительная проверка
импорта браузером упрощённая. Невалидный профиль не применяется.
Экспорт даёт переносимый JSON с настройками, без паролей Wi-Fi и телеметрии.

На самом круглом дисплее редактор открывается из настроек либо нажатием на виджет.
Там можно менять поля кнопками +/−, добавлять/удалять виджеты и применять результат.
Палитра цвета ограничена 6 значениями; единицы переключаются auto/явные текущие.
Произвольные строки единиц, точный RGB, заголовки и порядок экранов удобнее задавать
с телефона/JSON. Добавление новых **экранов** выполняется с телефона; дисплейный
редактор добавляет виджеты и циклически выбирает уже существующие экраны.

## Ограничения схемы и настоящего renderer

Схема [`bk_ui_config.h`](../../firmware/components/ui_config/include/bk_ui_config.h)
имеет `layout.version = 1`; обёртка профиля настроек использует `version = 3`.
Сейчас поддержаны:

- 1–8 приборных экранов, до 8 виджетов на каждом, минимум один включённый экран;
- 9 типов: NUMBER, DIGITAL, ARC, NEEDLE, BAR, TEMPERATURE, STATUS, ALARM, CHART;
- ID до 15 байт: ASCII-буквы, цифры, `_`, `-`, без повторений;
- название до 63 байт UTF-8, единицы до 15 байт UTF-8;
- RGB24, конечные min/max в пределах ±1 000 000, min < max;
- точность 0–3, варианты font_size20/48;
- JSON до 32 КиБ; UTF-8-байты и число видимых русских букв — разные величины.

Для прямоугольных виджетов валидатор проверяет углы относительно центра240/240
и радиуса232px; для круглых шкал проверяет вписанный круг. Внешние рамки должны
иметь x/y >=0, x+w <=480, y+h <=432. Есть минимальные размеры по типам, например
NUMBER не меньше120×110, CHART/BAR/TEMPERATURE не меньше64×64.
**Проверки взаимного перекрытия виджетов нет.** Можно создать валидную конфигурацию,
которая перекрывает другой виджет или общие заголовок/меню. Поэтому нужен просмотр.

Поля не означают произвольное управление всеми деталями оформления:

- `x/y/w/h` меняют внешнюю область. Внутренние отступы, подписи и размещение числа
  относительно единиц определяет реализация типа.
- У ARC сейчас угол270°, поворот135° и толщина12px. У NEEDLE — круглая шкала,
  фиксированные параметры делений и линейная стрелка. Эти свойства не входят в JSON.
- `font_size = 48` фактически переключает **цифры NUMBER** на Montserrat48.
  Подписи, DIGITAL и другие текстовые элементы остаются DejaVu Sans20.
  В форме телефона поле показывается всем типам, но это не делает их шрифт48px.
- `color` применяется к дугам, стрелке/делениям, заполнению шкал и линии графика.
  Обычный цвет чисел/подписей задаётся темой, цвет предупреждения — фиксированный
  красный. `color` не является произвольным цветом любого текста.
- Тёмный фон фиксирован. Стандартный зелёный0x126b48 в тёмной теме заменяется
  светло-зелёным0x72d6aa; произвольные цвета сохраняются.
- `unit` меняет подпись, но **не пересчитывает значение**. Например, написать°F
  вместо°C недостаточно для перевода температуры: нужна формула преобразования.
- Имя метрики берётся из C-реестра; произвольной подписи отдельного виджета пока нет.
- CHART хранит64 точки примерно по1секунде. Период, размер истории и форма линии
  не задаются JSON. Статус связи показывает общий connected, а не выбранную метрику.
- Неизвестная скорость, запас хода и другие отсутствующие данные остаются
  недоступными независимо от выбранного дизайна.

## Насколько декларативны системные страницы

Пять системных видов создаются отдельными ветками `show()` в
[`ui_core/bk_ui.c`](../../firmware/components/ui_core/bk_ui.c):

| View ID | Страница | Данные можно менять через API | Разметка из JSON |
|---|---|---|---|
| 5 | Главное меню | Тема и переход к последнему прибору | Нет |
| 6 | Wi-Fi / QR | SSID, пароль, URL, статус сети | Нет |
| 7 | Ошибки ЭБУ | Коды, достоверность списка, lookup описаний | Нет |
| 8 | Настройки / вход в редактор | Тема, яркость, параметры приборов | Нет |
| 9 | HUNTER | Статус связи, целевой экран после заставки | Нет |

Приборные слоты0–4 соответствуют view0–4; дополнительные слоты5–7 — view10–12.
Привязка определена в `bk_layout_view_to_screen` / `bk_layout_screen_to_view`.
Системные страницы не занимают квоту восьми приборов, но и заменить их профильным
экраном нельзя. Общие меню/статус и маска480×480 также остаются частью C renderer.

## Как сделать совершенно новый дизайн

Если хватает существующих компонентов, работа ограничивается профилем:

1. Экспортировать исходный JSON как резервную копию.
2. Собрать композицию с телефона либо изменить JSON; сохранить хотя бы один
   доступный стартовый прибор.
3. Проверить точный результат общим simulator:

```sh
./build/simulator/bk_sim --import my-profile.json --export edited-profile.json
./build/simulator/bk_sim --import my-profile.json --render build/simulator
```

4. Импортировать проверенный профиль в телефонный редактор и нажать «Сохранить».
   Приготовленные примеры находятся в [`simulator/profiles`](../../simulator/profiles).

Если нужны иной рисунок шкалы, сложная стрелка, новая форма графика, собственные
картинки или движения, требуется работа разработчика в UI:

1. Изменить существующий тип в `ui_widgets` либо добавить новый тип в enum
   `bk_widget_type_t`, `bk_widget_registry`, `bk_widget_create/update`.
   При сохранении прежних enum-номеров старые профили не меняют смысл.
2. Для новых параметров дополнить конфигурацию, validator, JSON parser/exporter
   и телефонную форму. Если формат меняется несовместимо, поднять версию и
   предусмотреть миграцию старых профилей.
3. Для SVG/собственных изображений сохранить исходный ресурс и встроить
   подготовленный LVGL-ресурс в сборку. Текущий профиль не умеет загружать SVG
   через Wi-Fi. Простой путь — предварительное преобразование в bitmap/C image;
   настоящему SVG decoder нужны отдельное подключение, конфигурация и проверка.
4. У стрелки можно заменить line-геометрию на собственный векторный путь или
   изображение с заданным центром вращения. Сглаживание, easing, цветовые зоны,
   тени и переходы добавляются в widget renderer/анимации, без запросов в ЭБУ.
5. Собрать simulator, проверить состояния UNKNOWN/STALE и предупреждения,
   затем собрать ESP-IDF и проверить память/FPS/отсутствие tearing на дисплее.
   Загрузка новой прошивки нужна один раз для нового типа/ресурса; дальнейшие
   комбинации этого типа снова можно менять профилями, если его свойства
   предусмотрены схемой.

Для обычного редизайна не требуется трогать `mikas`, `kline`, USB-транспорт или
планировщик опроса. UI получает готовые значения через `bk_ui_set_sample`.
Изменения протокола нужны только при добавлении данных, которых текущий источник
ещё не предоставляет, а не из-за новой стрелки или другого расположения числа.

Эта матрица составлена по текущему коду, а не по визуальному макету. Для данной
документационной правки UI-код не изменялся; новые аппаратные испытания не выполнялись.
