# USB-KKL / FT232RL: отдельная прошивка

Этот вариант использует существующий USB-KKL вместо наших плат и прямого UART.
Протокол monitor0B, декодеры, UI и настройки остаются общими. Компьютер для
работы прибора не нужен. Потребуются готовый USB-A female разъём/пигтейл,
штатный 12P-кабель Waveshare, два22Ω и один стабилизированный источник5V2A.
Полная [схема подключения](../wiring/USB_KKL.md) описывает точные выводы и питание.
Это реализация для проверки на стенде: реальный кабель и автомобиль здесь не подключались.

## Совместимость

Цель — **FTDI0403:6001**, интерфейс0, FT232RL/FT232R. Этот идентификатор использует
собственный прежний проект; пользователь сообщает о работающем FT232RL-кабеле.
Приложенный ftdibus.inf — FTDI CDM2.08.14 от18марта2011 и содержит также другие
FTDI PID. Сам INF не определяет физическую модель адаптера. Его Windows DLL,
SYS, CAT и LIB не переносятся на ESP32 и не включены в репозиторий.
Работающий Windows-драйвер владельца заменять не требуется.

В ESP используется **официальный драйвер Espressif usb_host_ftdi_vcp2.1.1**,
CDC host2.4.1 и nativeUSB Host ESP-IDF5.5.1. Снимаются служебные FTDI байты;
IN-buffer=0 выбирает endpoint MPS64B для одного FT232 full-speed пакета. Последовательный
режим9600,8N1, без flow control, DTR/RTS=True как в pyserial прежнего проекта,
latency2ms. Эхо и checksum проверяются так же, как с UART. OBD-II не подставляется.

## Перед прошивкой

1. Полностью отключить R2-жгут от дисплея: GPIO19 нужен D−, не TX_ARM.
   Одного снятия JP1 недостаточно для освобождения USB-линий.
2. KKL отключить от компьютера и USB Host на время прошивки. Не выбирать его
   COM-порт в esptool: прошивается **дисплей**, не диагностический адаптер.
3. Подключить ПК к **USB TO UART/CH343, J2** Waveshare. NativeUSB/J3 не используется
   для прошивки этого сценария. На исходной2.1 нет ручного USB-select.
4. Выбрать COM-порт именно CH343 дисплея. В диспетчере устройств он появляется
   при подключении USB TO UART. Если есть сомнения, временно отключить остальные
   USB-UART устройства и проверить появление/исчезновение нужного порта.

## Windows10 / ESP-IDF PowerShell

Установить ESP-IDF5.5.1 как в [основной инструкции](R2.md). Из папки firmware:

```powershell
$usbSdkConfig = Join-Path (Get-Location) "sdkconfig.usb-kkl"
$usbArgs = @("-B", "build-usb-kkl", "-D", "SDKCONFIG=$usbSdkConfig", "-D", "SDKCONFIG_DEFAULTS=sdkconfig.defaults;sdkconfig.usb-kkl.defaults")
idf.py @usbArgs set-target esp32s3
idf.py @usbArgs build
idf.py @usbArgs -p COM7 flash monitor
```

COM7 заменить портом дисплея. Отдельный build и sdkconfig сохраняют прежний
UART-профиль. В USB-KKL включены BK_ENABLE_KLINE и BK_TRANSPORT_USB_KKL;
BK_TRANSPORT_UART исключён. Основная consoleUART0 включена для стендовых логов
на CH343; native USB CDC/Serial-JTAG выключены. UART backend с GPIO19-ARM
в эту сборку вообще не компилируется.

Linux/macOS: те же аргументы `-B build-usb-kkl`, отдельный абсолютный SDKCONFIG
и строка `-D 'SDKCONFIG_DEFAULTS=sdkconfig.defaults;sdkconfig.usb-kkl.defaults'`.
В menuconfig можно выбрать `BK Mikas R2 → ECU transport → USB Host + FTDI`,
но нельзя смешивать GPIO19-ARM и nativeUSB на одном жгуте.

Для возврата к R2 UART использовать обычную сборку build с BK_TRANSPORT_UART
и выключенными консольными UART/USB. Подключать R2-жгут только после остановки
USB-режима и изменения проводки при снятом питании.

## Первый запуск

Сначала собрать проводку с отключённой машиной и проверить5V/полярность/GND.
Подключить KKL к готовому USB-A female; его внешние5V и питание J9.2 дисплея
берутся от одного источника отдельными ветвями. D− идёт через22Ω наJ9.3,
D+ через22Ω наJ9.4. NativeJ3 пустой. J9.12 — GPIO0, не масса.

Для автономной работы убрать ПК-кабель с CH343. Для стендового monitor его
можно оставить в отдельном UARTJ2, если питание организовано по схеме и
не подключён R2-жгут: USB Host работает на другом, nativeUSB блоке19/20.
Не подключать второй USB-хост к тем же D±. Простая надпись OTG на кабеле не
обеспечивает питание и правильную роль Type-C на device-порту Waveshare.

В monitor ожидаются сообщения `USB Host ready` и затем `FT232RL opened`.
При отключении/подключении кабеля код повторяет открытие адаптера и инициализацию
monitor0B; при отсутствии ЭБУ UI работает и показывает отсутствие связи.
Если USB-кабель определился, но ответа ЭБУ нет, это ещё не ошибка экранов:
сначала проверить прежний жгут/зажигание/питание KKL и эхо.

Затем подключить автомобиль **точно тем проверенным кабелем/переходником**,
которым уже работают OpenDiag и прежний проект. Не переносить12V на USB5V,
не разбирать KKL ради его внутренних TX/RX. Для K-Line используется электроника
самого KKL; его питание от автомобильного разъёма сохраняется как раньше.

## Проверка результата и диагностика

В локальном веб-интерфейсе отображается активный транспорт и готовность адаптера.
В `/api/telemetry` после входа: `transport`, `adapter_ready` и `connected`.
Готовность адаптера означает открытый USB/VCP, `connected` — ответ monitor0B ЭБУ.
Ошибки эха, кадра и таймауты подписываются в UART-логе при изменении состояния;
данные с ошибкой не показываются валидными. Не публиковать пароли/серийные номера.

- Нет `FT232RL opened`: проверить5V, D±/GND,22Ω, отсутствие второго хоста,
  точный VID/PID и оригинальную ревизию дисплея. Другие USB-чипы автоматически
  не выбираются. Hub-сценарий отдельно не проверен.
- Адаптер готов, ЭБУ нет: проверить зажигание, существующий автомобильный
  переходник,9600/8N1, ответ0B и эхо. Windows OpenDiag с тем же кабелем —
  отдельная контрольная проверка; один USB-кабель имеет только одного хоста.
- Переполнение RX или framing/parity/overrun: текущий обмен отвергается,
  буфер очищается перед повтором. Проверить проводку и питание.
- Во время OTA USB-backend останавливает отправку запросов, но не имеет
  аппаратного выключателя K-Line внутри стороннего KKL. Это не эквивалент JP1.
  Обновлять при остановленном двигателе; для полной электрической изоляции
  отключить диагностическую ветвь/кабель.

Без физического дисплея/KKL нельзя подтвердить enumeration, восстановление USB,
токи питания и обмен с автомобилем. Сборка и тесты потокового обмена подтверждают
код и обработку ошибок, не результаты такого испытания.

### Примечание для разработчика транспорта

DTR/RTS задаются FTDI SIO_MODEM_CTRL с write-mask и value=0x0303,
не CDC-запросом к FTDI. Формат масок соответствует публичному
[ftdi_sio.h](https://github.com/torvalds/linux/blob/master/drivers/usb/serial/ftdi_sio.h).
Служебные RX-байты снимает закреплённый Espressif FTDI driver, а application
кольцо защищено от переполнения. Serial error сохраняется до нормального
serial-state, поэтому сброс кольца не скрывает продолжающийся framing error.
Windows-бинарники пользователя не исполняются и не нужны этому транспорту.
